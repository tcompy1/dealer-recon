# Operational resilience

## Restart policy

Production Compose declares `restart: unless-stopped` for PostgreSQL, backend and frontend. A deliberately stopped container stays stopped across daemon restarts; the operator must explicitly start it after maintenance. Retain the existing images, database volume, health checks, dependencies and loopback-only publications.

Compose startup orders DB healthy → backend ready → frontend. Docker daemon recovery does not enforce Compose dependency ordering. The backend can initially fail while PostgreSQL starts; convergence must be tested with the selected runtime and images. An unhealthy but running container is not automatically restarted by this policy. Do not add a competing host restart loop.

Repository integration does not update existing production containers. Applying the policy later needs a separate attended authorization and identity/backup preflight. A reviewed `docker update --restart unless-stopped` targeting exactly the three verified existing IDs can avoid recreation; preserve matching Compose configuration. Rollback restores the previous policy (`no`) on those same IDs and reverts only the three Compose entries, with explicit manual outage coverage. Never remove a volume or change public bindings as a policy rollback.

Fort Worth remains disabled. No migration, application deployment or production reboot is part of this configuration change.

Repository verification on 2026-10-19 exercised Docker 27.5.1 in a disposable Linux daemon with invented readiness tables and the retained approved-source rehearsal images. Passed: exact rendered-config comparison (only three restart fields), backend convergence after delayed DB startup, daemon restart recovery, deliberate stop across daemon restart, clean/nonzero process exit restart, and running-unhealthy nonrestart. This was not a physical VPS reboot or a production operation; amd64 application images ran on the local arm64 Docker host. No startup retry code was needed for the observed convergence.

## Backend idle database failures

The server entry point installs one pool error listener before its first query. PostgreSQL removes a failed idle client; the handler emits `postgres_idle_client_error` with an allowlisted code (otherwise `UNKNOWN`). It never logs connection details, SQL, client objects or exception text. A reporter failure uses a fixed safe fallback event. This does not retry failed requests or financial writes, and it does not change the shared pool factory used by CLI tools.

A real child-server regression terminates only its owned idle connection in a disposable database: the old server exits 1 with uncaught `57P01`; the patched server records the safe event, survives and reconnects. Tests also reject readiness while connections are unavailable, recover readiness afterward, and prove an interrupted checked-out transaction rolls back without replay. Deploying this code requires a new approved image/deployment; setting a restart policy alone does not install it. Database schema/migrations and financial behavior are unchanged.

## Passive monitoring contract

The repository supplies Python 3.9+ standard-library scripts in `scripts/operations/`; no package installation, public port or database role is added. Python timezone data must include `America/Chicago`. Linux/systemd installation and all provider configuration remain separately authorized work. Templates run as the existing `trent` operator, which must already have the reviewed local Docker access. Do not grant a monitoring provider Docker, SSH or database credentials. Docker access itself is privileged; external heartbeat URLs permit signal submission only.

| Script | Behavior | Exit/result contract |
|---|---|---|
| `resilience-check.py` | Default dry evaluation; `--send` enables signal delivery and private state persistence | 0 service probes healthy; 1 service/disk failure; 2 incomplete/invalid evaluation; 75 overlapping poll. Backup status is a separate event/check; service exit 0 does not mean backup/review success. |
| `send-heartbeat.py CHECK SIGNAL` | Explicit operator helper; check allowlist and `start`, `success`, `fail` only | 0 accepted delivery, 1 failed delivery. Never use it to invent a review or mask an outage. |
| `scheduled-backup-monitor.py` | Invokes the existing repaired backup wrapper exactly once, retains both streams privately | Returns original wrapper status (signals as 128+signal); 70 only if no wrapper result was obtained. Wrapper exit 0 with invalid archive is still recorded/notified as failure. |

Service evaluation checks exactly the three pinned container IDs/images and Compose project/service labels, running/health state, unpublished DB, exact loopback backend/frontend ports, Caddy active, both local HTTP endpoints, and a bounded `BEGIN READ ONLY; SELECT 1; COMMIT`. PostgreSQL and backend require explicit Docker `healthy` status. The frontend may have no Docker Health field: the allowlisted inspection projects `health=none`, not `healthy`, while still requiring the pinned identity/image, running state, loopback binding and HTTP success. A reported frontend `unhealthy` status fails. It reads no customer records. Disk failure is less than 10 GiB free or greater than 85% used. Docker subprocesses have five-second limits, DB connection/query limits are three seconds, and an overall 45-second evaluation deadline plus a 55-second systemd limit prevent hung checks from sending reassuring success. A nonblocking lock prevents overlap.

Services are evaluated every minute: first failed observation withholds success; the second sends failure. Backup freshness is checked every five minutes and fails immediately if the latest published archive is invalid or older than 26 hours. An incomplete/killed evaluator does not send success. The provider's independent missing-heartbeat deadline must detect absent execution; local code alone cannot deliver an outage email when the host is down.

Implementation refinement from the reviewed plan: freshness rehashes the full latest archive on every five-minute evaluation instead of trusting a metadata cache between daily rehashes. This simplifies integrity state and strengthens checking for currently small archives. Measure hashing time against the 45-second budget before installation and when archives grow. Exceeding the budget fails closed; do not skip integrity verification to keep a heartbeat green.

Four independent checks preserve four distinct facts: local service health, scheduled backup outcome, valid-backup freshness, and explicit daily operator review. A manual backup can improve freshness but cannot clear a failed scheduled run. Archive integrity is not restore verification. Preserve the separate restore evidence and recovery pin.

## Private configuration and records — not installed

After separate approval, root owns the immutable scripts in `/usr/local/lib/dealer-recon-monitor` (0755 directory; 0644 source). `/etc/dealer-recon-monitor` is private to the executing operator (0700), with 0600 files: `containers.json` and `service-health.url`, `backup-freshness.url`, `scheduled-backup.url`, `daily-review.url`. Files must have the same owner as their parent; configuration owner must be root or the executing UID for heartbeat delivery. These scripts reject symlink credential files. Do not put URLs, tokens, environment values or connection strings in Git, shell history, argv or journals.

`containers.json` is an object with exactly `db`, `backend`, `frontend`, each containing `id` (full 64-character lowercase Docker ID) and `image` (`sha256:` plus 64 lowercase hex characters). Record verified identities through the approved production preflight. Refresh this file only during an authorized deployment after reconciling actual identities; do not auto-discover and accept drift.

`/var/lib/dealer-recon-monitor` is 0700, owned by the operator. It contains private atomic `state.json`, `poll.lock`, and a separately provisioned 0700 `reviews` directory. `--send` updates counters and last review delivery. Dry evaluation may create the lock but sends nothing, changes no backup/application records, and does not update monitoring state. URL files accept only HTTPS `hc-ping.com` UUID endpoints. Delivery verifies TLS, rejects redirects and ambient proxies, uses empty POST bodies, and has a hard four-second total deadline including DNS. No retries. Only opaque check identity and status leave the machine. Safe event/reason codes remain in the journal; delivery failure never changes backup success or its original exit.

The systemd templates define a oneshot service and minute timer, not a new application supervisor. They do not restart Docker, Caddy or application services. Before installation verify the actual `trent` identity, Python path/timezone support, Docker access, private directory ownership, existing backup paths and service names. The sandbox permits writing only private monitoring state and requires read access to managed backups/configuration. Syntax/unit validation is weaker than exercising the unit under the actual host's systemd and permissions; an attended dry run under that identity is a deployment gate.

## Scheduled backup adapter

The reviewed installed wrapper is `/usr/local/sbin/dealer-recon-backup`. Its retained October 19 baseline SHA256 is `eb632eb8ce14dd4a7b0e9d2c713cc3b89932d5b92bbf42f2bb6d5f32620760d8`; this is prior inspection evidence, not a fresh production check in this repository-only change. Stop activation on drift and review the new interface rather than replacing it with the generic repository helper.

On success the wrapper prints exactly one new absolute directory under `/opt/backups/managed`, named `YYYYMMDDTHHMMSSZ.<unique>.archive-ok`. The adapter requires a new path created during this invocation, private permissions, `record.json` status `ARCHIVE_VALIDATED_RESTORE_NOT_TESTED`, zero `pg_dump_exit` and `archive_list_exit`, ordered nonfuture UTC timestamps, positive recorded size, a nonempty `archive.list`, empty `stderr.log`, no `FAILED` marker, and matching `SHA256SUMS`/full dump bytes. It never uses a pre-existing archive as scheduled success. This validates the wrapper's archive evidence; it does not run another backup, restore, migration or retention pass.

The adapter retains paired private `adapter-<unique>.stdout` / `.stderr` diagnostics under the managed backup directory, including unsuccessful wrapper output. Original exit status survives later diagnostic fsync/read/validation errors. Private diagnostic persistence failure is separately visible and cannot count as validated scheduled success. Launch failure reports 70. The existing wrapper owns its backup lock and dump promotion; no retry-until-green or alternative dump logic is added. No timeout kills a running backup: the independent scheduled-check start/grace deadline alerts on a hang. A killed adapter produces no success signal; investigate the wrapper's actual run before any manual retry.

A future approved cron change must replace exactly the one existing repaired-wrapper command with `/usr/bin/python3 /usr/local/lib/dealer-recon-monitor/scheduled-backup-monitor.py`, retaining its existing `0 2 * * *`, America/Chicago schedule and private scheduler-log redirection. Do not add a second cron job, discard errors, change the repaired wrapper, remove historical files or rotate diagnostics in this task. Retention/log rotation is a separate reviewed follow-up. Monitor disk growth meanwhile.

## Daily human review and notification activation

The owner remains the primary responder and has accepted temporary daily review. No mailbox, provider account, backup responder or continuous coverage is established by this code. UptimeRobot plus Healthchecks are the assessment's proposed providers; selection, current free-plan eligibility, accounts, mailbox and email delivery require separate approval. No external notification was sent during repository testing.

Proposed independent provider settings remain: public HTTPS `/`, `/health`, `/ready` every five minutes; service heartbeat period 60 seconds/grace 120 seconds; freshness period five minutes/grace five minutes; scheduled backup `0 2 * * *` America/Chicago with two-hour grace; human review due 10:00 America/Chicago with one-hour grace. Confirm actual provider scheduling and email behavior before activation. Do not claim dual-stack monitoring unless separately verified.

After actually reviewing the scheduled outcome, latest age/checksum, private failures/journal, capacity, restore evidence and open incidents, the operator writes a private `reviews/YYYY-MM-DD.json` for the current America/Chicago date. Schema: `reviewer` nonempty text, `reviewed_at_utc` an actual timezone-aware timestamp, and `checked` with exactly these boolean-true fields: `scheduled_outcome`, `backup_age`, `checksum`, `failure_log`, `disk`, `restore_evidence`, `open_incidents`. Record actions/next owner separately in the incident record. Never backfill missing reviews or mark an unchecked item true. The evaluator preserves early review records but defers daily-review success until 10:00 America/Chicago or later, after validating the current-day record. This matches the existing 10:00 cron check and one-hour grace; an earlier heartbeat would apply to the preceding cron window. Late reviews can still clear the alert that day. After confirmed delivery and successful state persistence, subsequent polls suppress sends for that local date. Failed or unconfirmed deliveries remain eligible on the next normal poll; delivery is not strictly exactly once. Daylight-saving repeated hours do not create another day. The record is an operator attestation: the evaluator validates its structure and timestamps, not the truth of a dishonest completed attestation. Never fabricate review evidence.

Activation gates: owner-selected mailbox and accepted response/coverage targets; named substitute or explicit single-owner limitation; tested DOWN/recovery/failure/missed-heartbeat delivery and acknowledgement; fresh production identity/backup preflight; attended dry-run evaluation; deliberate synthetic provider tests; observation of the next authorized scheduled run and human review. No account, install, cron change or extra production backup is authorized by repository integration.
